# ADR 0006 — Composition is a dict, and a person is a cell with a deadline

- **Status:** Accepted
- **Date:** 2026-08-29
- **Phase:** 4b (Composition and human cells)

## Context

AGENTS.md §Phase 4 asks for two things ADR 0005 deferred: "cell composition is a plain DAG of
calls, described in data, not a framework", and a `HumanQuery` — "a Cell whose instrument is a
person", with a price in wall-clock, a deadline, and a fallback if the deadline passes.
"Humans are resources in the network with the same accounting as models" is the sentence that
decides most of what follows.

Both are places where the standard answer is a framework. Composition usually arrives as a
scheduler with node classes and a lifecycle; a human in the loop usually arrives as a blocking
prompt with no price and no bound.

## Decision

### A graph is a `dict[str, Node]`

No builder, no executor, no node base class, nothing concurrent. `order` returns a
topological sequence and `run` walks it. §Style says a cell graph is a dict, not a subclass
tree, and there is nothing here that a dict does not already do.

Data flows through `needs`, which is simultaneously the edge list and the substitution table —
one piece of data, so the edges and the dataflow cannot disagree.

**`$name` and `string.Template`, not `{name}` and `str.format`.** A task is prose, and
research prose routinely contains braces: JSON, code, set-builder notation. `format` would
treat all of it as syntax and fail on a task that is merely *quoting* something. A placeholder
with nothing to fill it raises rather than substituting an empty string.

**Ready nodes are taken in name order**, not dict-insertion order, so the same graph runs its
steps in the same sequence whoever assembled it. Two identical graphs then produce identical
ledgers, and a diff between two runs is about the runs.

**A failed node stops the graph.** Nothing downstream runs. Carrying on with the nodes that
still can produces a partial result shaped exactly like a whole one, and nothing in the record
would say which parts were missing.

**Every node reserves and settles on its own.** No graph-level budget, so
`costs_attributed_to_a_wager_sum_to_the_session_total` still holds, and a graph that dies
halfway has spent exactly what its finished nodes cost.

### A person returns the same `Run` a model does

Same reservation, same ledger, same `plays` edge, same interned transcript. The only
differences are what a person costs (`human_seconds`, measured wall-clock) and that they can
fail to reply at all.

**A question is a prompt, so it is versioned like one:** `playbook_version:<role>-<hash of the
question>`, sharing `playbook.version_of`. Reword the question and you are asking something
else; a person's answer stays attributed to the words actually put to them.

**The fallback covers the deadline and nothing else.** A person who answers in the wrong shape
is a failed run, exactly as a model would be. Substituting the fallback there would write
"nobody answered, so we assumed this" over the top of somebody who *did* answer — a lie in the
record, and precisely the class of self-deception this project exists to prevent.

**Falling back is on the `Run`, not buried in the transcript.** `fell_back` is a field because
a graph downstream of a fallback is running on an assumption rather than an answer, and a
caller must be able to tell those apart without parsing prose.

**The fallback is schema-checked before anything is reserved**, so a fallback that could never
be used is a configuration error found in the first millisecond, rather than at the deadline
an hour later with the question already asked.

### The asker is a file drop, not a console prompt

`FileDrop` writes `<run>.question.json` into a configured queue directory and waits for
`<run>.answer.json` beside it. A blocking `input()` was the obvious alternative and is wrong
for three reasons: g0rd0n runs unattended, so there may be no terminal; a person is not
available on the timescale of a process, so the question must outlive the asker; and a
console prompt leaves no record of what was asked.

A half-written answer file is an **error, not a timeout**. Someone is editing it by hand, and
treating a partial JSON document as "nobody answered" would fall back while a person was
mid-sentence.

The queue directory is a config key. A directory invented by a caller is exactly the ambient
state `config.py` exists to prevent, and it cannot live under the vault, which gets dropped
and regenerated by `vault rebuild`.

## Why this design

- **Against a scheduler or executor abstraction:** nothing here is concurrent, and a
  sequential walk of a topologically sorted dict is the whole requirement. Concurrency would
  also make the ledger's ordering non-deterministic for no measured benefit.
- **Against a graph-level budget:** it would need a fourth `Ledger` operation, or a
  reservation that several nodes draw on, and `no_priced_call_without_a_reservation` pins
  that surface deliberately (ADR 0001).
- **Against continuing past a failed node:** a partial result that looks whole.
- **Against `HumanQuery` subclassing `Cell`:** they share a result type and an accounting
  discipline, not a structure — a person has a deadline and a fallback, and no playbook,
  tools, or turns. `graph._play` is two cases in one function, which is smaller than any
  hierarchy that would unify them.
- **Against making the fallback cover every failure:** it would make "we heard from a person"
  unfalsifiable from the record.

## Failure modes

- **A fallback silently carrying a graph.** Real: nothing stops a caller from ignoring
  `fell_back`. Mitigated only by it being on the result rather than in prose. When Phase 7
  has Wagers, a verdict resting on a fallback should probably be `inconclusive` rather than
  anything else — that belongs there, not here.
- **A stale answer file.** `FileDrop` keys on run id, which is a fresh uuid unless a caller
  passes one; a caller reusing a run id would pick up the previous answer.
- **A long deadline blocking everything.** Deliberate and unbounded by design — a person's
  deadline is the person's, and there is no timeout on the timeout. `seconds` is reserved and
  overspend is checked, so a query that waits far past its estimate is refused at `spend`.
- **No concurrency.** Two independent nodes run one after the other even though nothing
  connects them. Fine at this size; the moment it is not, this ADR needs revisiting rather
  than a thread pool appearing in `run`.

## How it is tested

The deadline tests use real wall-clock, kept to tens of milliseconds. A fake clock would test
the fake, and the thing under test is whether a deadline actually expires — the minimum test
`human_query_times_out_to_its_declared_fallback` runs the real `FileDrop` against a real
directory with nobody there.

Each invariant was checked by breaking it: the fallback made to swallow a malformed answer,
`fell_back` pinned to `False`, the deadline made to expire instantly, cycle detection removed,
ready-node ordering taken from the dict, and `Template` swapped for `format`. All six failed.
The third is worth noting — a deadline that never actually waits is caught by the assertion
that `human_seconds` is at least the deadline, not by the fallback assertion, because a
broken deadline still *produces* a fallback.
